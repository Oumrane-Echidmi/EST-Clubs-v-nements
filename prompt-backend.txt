## 6. P0 — Core backend

### Authentication

Implement:

- POST /api/auth/register
- POST /api/auth/login
- POST /api/auth/refresh
- POST /api/auth/logout
- POST /api/auth/forgot-password
- POST /api/auth/reset-password
- GET /api/auth/me

Requirements:

- Every public registration creates a STUDENT.
- Passwords require at least eight characters, including a letter and number.
- Hash passwords with bcrypt.
- Access tokens expire after 15 minutes by default.
- Refresh tokens expire after 30 days by default.
- Store refresh-token hashes only.
- Rotate refresh tokens atomically.
- Detect refresh-token reuse and revoke the corresponding token family.
- Use current database roles and active status for authorization.
- Implement expiring, single-use password reset tokens.
- Implement a MailService interface with console development transport and optional SMTP.
- Prevent account enumeration during password recovery.

### Users and profiles

Implement:

- GET/PATCH /api/me
- PATCH /api/me/password
- PATCH /api/me/notification-preferences

Validate all user-controlled input.

Never permit a user to change their own role through profile endpoints.

### Clubs

Implement all original club endpoints:

- Club list and details.
- Club creation, editing and deletion.
- Search and category filtering.
- Follow and unfollow.
- Club events.
- Authorized club members.
- Club status management.

Students see only approved clubs.

Resolve club ownership through ClubMember with role ADMIN.

Return 403 when a club administrator accesses another club's protected resource.

### Events

Implement:

- Event list and details.
- Event CRUD.
- Search and filters.
- Approval and rejection.
- Scoped administrator access.

Club administrator events start as PENDING_APPROVAL.

Super administrator events may be automatically PUBLISHED.

Editing major fields of a published event as a club administrator returns it to PENDING_APPROVAL.

Prevent lowering capacity below active registrations.

Every event response includes:

- registeredCount
- availableSeats
- phase
- registrationState
- serverTime

Also expose the current user's registration ID and cancellation eligibility when applicable so Flutter can render the correct action without inventing business rules.

Use grouped registration counts for list endpoints. Avoid N+1 queries.

### Registrations

Implement:

- POST /api/events/:id/register
- DELETE /api/registrations/:id
- GET /api/me/registrations
- GET /api/events/:id/registrations
- PATCH /api/registrations/:id

Registration must use a Prisma interactive transaction with PostgreSQL SELECT FOR UPDATE on the event row.

Inside the transaction:

1. Lock the event row.
2. Validate event existence, publication status and registration deadline.
3. Reject duplicate active registrations.
4. Count CONFIRMED and ATTENDED registrations.
5. Reject if capacity is reached.
6. Create a registration or reactivate an existing CANCELLED registration.
7. Commit.

Use the same event-row locking strategy for operations that change capacity or registration occupancy to prevent concurrent inconsistencies.

Calculate:

availableSeats = capacity - activeRegistrationCount

Never allow overbooking.

Cancellation must respect ownership, administrator scope, event start time and configured cancellation cutoff.

Return stable error codes:

- EVENT_FULL
- ALREADY_REGISTERED
- REGISTRATION_CLOSED
- CANCELLATION_NOT_ALLOWED
- FORBIDDEN
- NOT_FOUND
- VALIDATION_ERROR

Create registration notifications after commit. Notification delivery errors must not invalidate a successful registration.

### P0 seed

Provide an idempotent development seed sufficient for frontend integration.

Include student, club administrator and super administrator accounts, clubs, events and registrations.
